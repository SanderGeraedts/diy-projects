# Goal

Sander, on 2026-11-22, about dropping photos onto a project: "Preferably zip files with
images as well, but the latter is no deal breaker."

T-0031 lets the owner drop image files onto a project page. After this task, as D-0034 says,
a `.zip` dropped there (alone or together with photos) is unpacked in the browser and its
images are imported like dropped ones:

- unpacked with **fflate**, added with `pnpm add fflate` (G-0016), loaded with a dynamic
  `import()` only when a zip is dropped, and precached so it works offline;
- entries are inflated and handed on **one at a time**, never the whole archive in memory;
- every file whose name ends in `.jpg`, `.jpeg`, `.png`, `.webp`, `.heic`, `.heif`, `.avif`
  or `.gif` (any case), in any folder of the zip, goes through `startImport` named after its
  name in the zip, and lands in the day it was taken; its unpacked bytes are the original
  (D-0015);
- skipped without a word: folders, other files, `__MACOSX/`, `._*` and other dotfiles; a zip
  inside the zip isn't opened;
- an image without EXIF is dated by its modification time in the zip when fflate gives it,
  otherwise by the zip file's own date, and listed as dated by the file, as today;
- listed as not added, with a reason: an image over 40 MB unpacked (unpacking it stops as
  soon as it passes 40 MB), and a zip that can't be read (damaged, encrypted or not a zip);
  a zip without images says so in the summary.

The picker doesn't take zip files (D-0033).

# Done when

1. CI on the pull request is green (`checks / checks`: `harness check`, typecheck, unit
   tests, build and the end-to-end tests), with no test that passed only on a retry
   (G-0031). Locally the developer runs typecheck and what the change touches.
2. `package.json` has `fflate` under `dependencies` and `pnpm-lock.yaml` has it, with no
   other new package: `pnpm why fflate` shows it only as a direct dependency, and
   `git diff main -- pnpm-lock.yaml` adds no package besides `fflate`.
3. fflate isn't in the startup bundle: after `pnpm run build`, the chunk that contains
   fflate's code isn't loaded on `/` (an e2e check on network requests, or `dist/index.html`
   and its entry chunk don't reference it), and it is in the service worker's precache list
   (`dist/sw.js` names it).
4. Unit tests on the unzip step, on zips built in the test with fflate's `zipSync` from
   generated bytes (no real photos):
   - a zip with `a.jpg`, `sub/b.JPEG`, `notes.txt`, `__MACOSX/._a.jpg`, `.DS_Store` and
     `inner.zip` yields exactly `a.jpg` and `sub/b.JPEG`, in that order, with bytes equal to
     what went in;
   - an entry larger than 40 MB unpacked comes out as a failure with a reason, and the
     entries after it are still yielded (the test may lower the limit through a parameter
     to keep the test small; the default is 40 MB);
   - bytes that aren't a zip come out as one failure for the zip, with a reason.
5. An e2e test (in `e2e/drop.spec.ts` from T-0031), desktop viewport, offline after the
   service worker is ready: dropping a zip with three generated JPEGs with EXIF dates on two
   days, one in a folder, plus `readme.txt`, together with one loose JPEG, adds 4 photos
   ("4 foto's toegevoegd."), puts them in their days as the picker would, and doesn't list
   `readme.txt`. Dropping a damaged zip lists it as not added.
6. The UX designer's review after the build, in *Design*, finds no differences.

# Notes

- **Depends on T-0031:** the drop on the project page, the split into files and failures,
  and the "not added" reasons come from there. This task adds a zip branch to that split.
- **fflate:** use its streaming `Unzip` (with `UnzipInflate`) to take one entry at a time;
  feed the zip `File` in chunks from `file.stream()`. Check whether the entry's modification
  time is available in the version installed; if not, use the zip `File`'s `lastModified`
  for photos without EXIF (D-0034).
- **Names in the summary:** files from a zip carry their path in the zip; how a failure or a
  "dated by the file" line shows that it came from a zip is the UX designer's.
- **Precache:** `vite.config.ts`'s `workbox.globPatterns` already takes every `.js`, so the
  lazy chunk is precached; Done when 3 checks it.
- **Memory:** a 40 MB cap per entry plus one entry at a time keeps a large or hostile zip
  from filling memory; the import itself then holds one photo at a time, as it does now.
- **No question for the Engineer:** a new npm package costs nothing, touches no
  infrastructure, data store, access or outside service, and is removed as easily as it is
  added (D-0034). No decision governs dependencies otherwise.
- Handed to the UX designer: the summary gains zip-specific lines, and any drop hint may
  mention zip files.
